# 写偏即停：语义版 TTSR

更新日期：2026-09-22。状态：实验，**默认关闭**；代码与测试已完成，没有在真实模型 + 真实 Jev 上跑过。

## 1. 来历

oh-my-pi（OMP）的 TTSR：用正则表达式盯着模型的流式输出，一旦匹配就中断输出、把对应规则摆到模型面前、让它从原处接着写。优点是便宜、即时；缺点是正则只能发现事先想到的写法。

mu 的版本把“发现写偏”换成判定器：每输出一段，就拿输出的**结尾**去对照用户自己的话，一条规则一个是非题。规则不需要写成模式，平常的话就行（“用中文回答”“不要写占位实现”“不要提到竞品的名字”）。

## 2. 怎么开

`mu.json`：

```json
{ "features": { "ttsr": { "enabled": true, "rules": ["用中文回答"] } } }
```

桌面端设置 → 功能 → “写偏即停”里同样可以开关、填规则。只想攒数据、不想真的打断：把判定点 `output.drift` 的模式设成 `shadow`。

| 选项 | 默认 | 含义 |
| --- | --- | --- |
| `rules` | `[]` | 一直要守的规则。任务帧里的硬约束会自动加入，不必重复 |
| `segmentChars` | 600 | 每新增多少字符的输出判一次 |
| `maxRules` | 4 | 每次最多对照几条；超出时保留用户最近说的 |
| `maxInterrupts` | 2 | 用户两次发言之间最多中断几次 |

## 3. 运行方式

1. 监听 `message_update`，累计正文和工具调用参数的增量（**思考内容不算输出**：它没有告诉任何人任何事，而且本来就可能在权衡用户排除掉的做法）。
2. 每满 `segmentChars`，取输出结尾最多 900 字符，问判定点 `output.drift`：“`recent_output` 是否违反用户的这条指示？‘……’”。判断与输出流**并行**，同一时刻只有一次判断在途，流从不等待。
3. 只有 `active` 模式下、判定器亲自给出的、确信的“是”才会动手：`ctx.abort()` 掐断当前输出。判定器慢了、拿不准、不可用，一律放行。判断回来时那条消息已经写完了 → 作废（写完之后的事归硬约束把关和完成核对管）。
4. 被掐断的那次运行**完全结束之后**（`agent_settled`），发一条 `kyrn.ttsr` 消息：点出是哪条指示，要求从断点继续、不要重复已写内容；已写部分如果本身违规，用一行说明并重做。

实现上的一个坑：不能在 `agent_end` 里发这条消息。那时运行还在收尾，消息会被当作 steer 排队，而被中止的运行会丢弃队列，模型永远收不到。测试里先撞到了这个问题才改到 `agent_settled`。

## 4. 与其它功能的关系

- **目标模式**：harness 自己掐断的运行不算“用户打断”（`runtime.harnessAbort`），目标不会因此暂停。
- **完成核对**：被掐断的半截输出不送去判“是否声称完成”。
- **硬约束把关**（`tool.constraint`）：照常在工具调用前把关。两者覆盖面不同：把关只看改动类的工具调用；写偏即停还覆盖纯文字输出（语言、格式、不该说的话），并且能在一大段 `write` 内容生成到一半时就停下，省下后半段的输出。

## 5. 代价与风险（为什么默认关）

- 每 600 字符输出多一次判定调用。按 2026-09-21 实测的 Jev 计费方式，长输出的会话里这笔开销不小；`segmentChars` 调大可以降频。
- 误判的代价是打断一次正常输出。用确信阈值、每轮上限和“只认判定器亲口说的”三道保险压低，但没有真实数据之前不知道误判率。
- 不被信任做 `relate` 的判定器（档案里 `relate: false`）答不了这个判定点，在它那里永远走兜底（不打断）。

## 6. 验证情况

已验证（`test/ttsr.test.ts`，5 个用例，faux 流式模型 + `MockJudgeProvider`，连跑 6 遍稳定）：一条规则一个问题、只读输出结尾；确信违规时输出被中途掐断（`stopReason: aborted`，长度小于全文），随后收到点名规则的消息并继续；判“否”、拿不准、`shadow` 三种情况下输出完整无损；`maxInterrupts` 用完后不再打断；任务帧里的硬约束会成为规则；功能关闭时一次判定都不发生。

未验证：真实 Jev 对“输出结尾是否违反某条指示”的校准与误判率；真实提供商在 abort 之后续写的质量（不同厂商对半截 assistant 消息的处理不同）；对输出速度很快的模型，判定延迟是否来得及在消息结束前返回。
