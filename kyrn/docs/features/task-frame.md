# 任务帧与待办清单

更新日期：2026-11-10（一轮结束时的清单通知，第 8 节；其余为 2026-09-22 的记录）。对应 PRD `06-harness-prd.md` 的 FR-02（P0）。代码在 `packages/kyrn-judge`：纯模型 `src/frame/`，决策 `src/decisions/task-frame.ts`，功能 `src/extension/features/frame.ts`，接缝在 `src/extension/runtime.ts`。

## 1. 它解决什么

之前只有一个替身：目标 = 会话第一条消息，当前子目标 = 最新一条消息。六个功能（预判、工具输出准入的测试日志分支、遗忘、中途插话、通知、漂移监控）都通过 `runtime.taskFrame()` 读它，所以任务变了以后，所有“和目标相关吗”的判断仍然对着第一条消息。PRD 自己举的反例是“保留原方案，但取消数据库变更”。

现在 `runtime.taskFrame()` 签名不变，返回的是从真任务帧导出的紧凑形状，六个消费者一行没改就一起升级。完整的帧在 `runtime.frame`，是否过期在 `runtime.frameStale`。

## 2. 帧里有什么

- 目标 `goal`
- 硬约束 `constraints`：**用户原话**，逐字拷贝，附出处（用户回合号 + 该用户消息的会话条目 id）。规则路径遇到超过 1000 字的消息只截取开头并标 `partial`，不改写。
- 当前子目标 `currentSubgoal`
- 验收条件 `acceptance`：每条有 id（`a1`、`a2`…，永不复用）、文字、是否完成、谁勾的、一行证据、谁加的。**它就是待办清单。**
- 未决问题 `openQuestions`
- 版本号 `version`、最后更新的回合 `updatedTurn`、这一版怎么来的（`first-message` / `writer` / `rules`）、裁判把那条消息读成了什么。

PRD 列的“预算”字段这次没有做。

## 3. 谁做什么

1. **第一条消息**直接生成第 1 版（目标 = 这条消息），不问裁判，不调模型。
2. 之后每条用户消息，裁判回答**一个选择题**（决策 `task.frame`，能力类别 `relate`）：

   > What does `user_message` change in `task_frame`?
   > `new_task` 开始了另一个任务 · `constraint` 加了一条必须遵守的规矩 · `correction` 说当前做法不对 · `subgoal` 进入同一任务的下一步 · `none` 什么都没变（闲聊、提问、放行）

   状态按“关键内容在前”排列：`user_message`、`task_frame`（目标、约束、子目标）、`recent_turns`（最近两条摘要，这样“好”“用第二个”才有意义）。

   策略：`constraint` 和 `correction` 导致同一种更新（把原话记为硬约束），而“保留原方案，但取消数据库变更”两者都是，所以先把两者的概率相加再过线（0.6）。如果确信“有变化”（变化类合计 ≥ 0.7）但哪一类都不到线，结果是 `unclear`：**不静默覆盖目标**，交给 writer 处理并倾向记成未决问题；没有模型时直接记成未决问题。回退值是 `none`。
3. **只有判断为有变化时**才让生成模型写新帧：优先用配置的 `writer`，否则用会话当前模型（`runtime.llm`，关思考）。要求严格 JSON，解析不过就拒收。
4. **代码保证（不靠模型自觉）**：
   - 每条约束要么是旧帧里已有的，要么是用户这条消息里的原文片段（容忍换行、多余空格、首尾引号、句末句号）。
   - writer 改写了（不是原文）→ 用字符二元组相似度找到用户消息里被改写的那一句，**换回用户原句**；找不到 → 不记为约束，写进未决问题。
   - 裁判读成 `constraint`/`correction` 的消息，帧里至少留下一条来自这条消息的原话约束，writer 漏了就把整条消息原样补上。
   - 约束和验收条件只在 `new_task` / `correction` 时才允许消失，别的更新里 writer 漏掉的会被原样保留。
   - 已勾选的验收条件保留勾选和证据；writer 改了措辞的那条要重新满足。
5. **完全没有模型可用**时走规则：新任务 → 目标换成这条消息（约束保留，验收条件清空）；约束/纠正 → 原话追加为约束；子目标 → 设为当前子目标。

## 4. 更新失败与“过期”

writer 调用失败、超时或返回坏 JSON：**保留上一有效版本**，把这条用户原话连同裁判的读法记到 `unmerged`（原因 `failed`），帧标记为过期，并写一条 `kyrn.frame` 条目（重启后仍记得）。过期期间：

- `runtime.taskFrame()` 给消费者的视图 = 上一版 + 按规则并入的新原话（例如失败的是一条纠正，视图里的约束列表就带着它）。权威记录不动。
- **遗忘**（`forgetting.ts`）整个阈值批次暂停，阈值保持待触发；已经缩过的结果照旧缩，缓存前缀不动。
- **测试日志准入**的 `jev` 策略降级为 `rules`（按目标筛选需要目标是新的；精确重复规则不读目标，照常工作）。
- 通用的分块准入（`tool.admission`）**没有加守卫**：它只判断“这一块是什么”，从不读任务帧，所以不依赖任务状态。

恢复：下一条用户消息到来时重试 writer（把没并入的原话一起给它）。**连续第二次失败就由规则接手**，逐字并入，生成新版本。所以过期最多持续到下一条用户消息。

“迟到”（更新还在跑，回合已经开始）同样算过期，落地后自动解除。“没人判断过”（决策关闭、shadow、裁判宕机）**不算**过期：那正是以前替身的工作方式，而且一个留在 shadow 的决策不应该关掉另一个已生效功能的筛选。

## 5. 事件顺序（我选了什么，为什么）

pi 对同一事件的处理函数按注册顺序**串行** await。预判在 `input` 里最多等裁判 6 秒。如果任务帧等预判返回后才开始问裁判，两次等待会首尾相接。

所以：

1. 更新在 `runtime.beginTurn()` 里启动（新增的 `runtime.onTurnBegin` 钩子）。预判处理 `input` 时第一件事就是 `beginTurn`，于是任务帧的裁判调用和预判的裁判调用**并行**。第 1 版在这里同步生成，所以本回合第一个判断的台账 `origin` 里已经是 `frame: 1`。
2. 预判读 `taskFrame()` 时，本条消息的更新还没结果，读到的是**这条消息之前**的帧。这是对的：它问的就是“这条消息和原来的任务什么关系”。（旧替身在这里有个毛病：`beginTurn` 之后最新消息已经成了“当前子目标”，等于拿消息和它自己比。）
3. `frame` 注册在 `preflight` 之后。它的 `input` 处理函数等这次更新，上限 `waitMs`（默认 3000 毫秒），**从消息到达算起**，所以预判等过的时间不重复计。只有 `active` 模式才等。
4. 超时不丢弃：本回合先用“上一版 + 这条原话”（`taskFrame()` 里作为当前子目标出现，`frameStale` 为真），更新完成后照常落地，条目和展示事件都记在**发起的那个回合**名下。给模型的说明随下一条用户消息一起发（没有用 steer 投递：模型已经答完时 steer 会平白多触发一轮回答）。
5. 更新排成一条链，一次一个，慢的不会覆盖新的。会话切换、树导航、关闭时 epoch 加一，之前发起的结果作废。
6. 其余五个消费者都在代理开始工作之后才读帧（工具结果、`context`、`turn_end`），天然晚于更新。
7. 预判关闭时（或 `only` 里没有它），本功能自己调 `beginTurn` 计数。
8. 运行中途打的消息（steer / followUp，包括被“中途插话”功能改道重发的）也会判断并更新，但从不等待，回合号记当前回合。

## 6. 持久化与回退

- 每个版本、每次勾选/新增、每次失败各写一条自定义会话条目 `kyrn.frame`（`schema: 1`）。条目不进模型上下文。
- **只在引起它的那条用户消息进入会话之后才写**（该回合第一次 `context` 事件时）。原因：`/tree` 回到某条用户消息时，pi 把叶子移到那条消息的**父节点**；如果条目写在消息之前，回退到这条消息后帧里仍带着它的影响。条目 id 也在这时补进约束的出处。
- 会话启动（含 fork、resume、reload）和树导航时，从**当前分支**上最后一条有效的 `kyrn.frame` 重建。坏条目被忽略。分支上没有任何帧条目的旧会话，用分支上第一条用户消息按规则生成第 1 版（只在内存里）。

## 7. 给模型看什么

不进系统提示（会破坏提示缓存）。`before_agent_start` 时，如果帧版本和上次告诉模型的不一样，附一条自定义消息 `kyrn.frame`（目标、原话约束及回合号、子目标、验收清单、未决问题、尚未并入的原话）。版本没变就什么都不发。第 1 版不发（内容就是用户刚发的那句话）。勾选不发（模型自己做的）。压缩之后重发一次：mu 的压缩会过滤掉 `kyrn.` 开头的消息，而约束不能跟着丢。

## 8. 待办：`todo` 工具

验收条件就是待办，只有一份清单。`todo` 的三个动作：`list`；`done`（id + 一行证据，没有证据拒绝）；`add`（模型自己发现的条目）。勾选和新增**不涨版本号**（是进度，不是任务变化），但和版本一样写 `kyrn.frame` 条目，所以回退、重启后清单一致。已在能力目录登记为 `tool:todo`，`exposure: "always"`。

完成核对（`turn.completion`，升到 v2，问题没改，只改了策略）：模型的收尾消息说“做完了”而验收条件还有未勾的，本回合唯一的一次提醒会**点名这些条目**；即使本回合没改文件也会提醒。原有的“改了文件但没跑过任何东西”的提醒照旧，两者可以出现在同一条提醒里。

### 一轮结束时告诉用户清单的进度

问题：没盯着运行的人回来，要读完模型的收尾消息才知道要的东西做完没有，而清单和每项的证据就在帧里。例子：

```
mu: this task's checklist, 1 of 2 done (the evidence is the agent's own):
  [x] the cursor survives a deleted row · users.test.ts: 14 passed
  [ ] limit is capped at 100
```

一轮运行完全停下来以后（`agent_settled`，这时不会再有核对把模型叫回去），清单非空、并且和上次告诉用户时不一样（有新增或勾选），mu 发一条通知：完成了几项，每项是什么，勾掉的项后面是模型当时给的那一行证据。通知不占输入框，桌面端显示成对话里的一行。

- 每次变化只说一次。清单没变的一轮什么都不说；重新打开的会话以当时的清单为准，不重说。
- 证据是模型自己写的，mu 没有验证过，所以标题里写明“依据是代理自己给的”。一项都没勾时不提证据。
- 不说的情况：用户停掉的一轮、被 harness 截断后重跑的一轮（等重跑的那一轮结束再说）、计划模式（计划批准前清单只是步骤）、没有界面的运行（`mu --print`、json）、子代理（它的清单由父代理读）。
- `features.frame.report: false` 关掉。

运行途中，清单的进度在终端底部的状态栏里：`Checklist 1/2` / `清单 1/2`（状态键 `mu.checklist`），清单有条目时才有，每次新增或勾选时更新，清单空了就撤掉。想知道做到哪了，看一眼就行，不用问代理，也不用等这一轮结束。桌面端不显示这一行：它只认自己知道的状态键，清单的每次变化在判定面板的事件日志里（`frame.updated`）。

没有清单就没有这条通知：会话的第一条消息不调 writer，清单是空的，除非模型自己用 `todo add` 记了条目，或用户批准了一份计划。没有测量过：真实任务里有多大比例在结束时有清单。

## 9. 三种模式下的含义

| 模式 | 裁判 | 帧 |
| --- | --- | --- |
| `off` | 不问 | 第 1 版 + “最新消息 = 当前子目标”的规则视图，与旧替身给消费者的完全一样。`todo` 和 `/frame` 可用 |
| `shadow` | 问，结论记入台账（`judged`） | 同上。**不调 writer、不涨版本、不发说明**。任务帧是基础设施，所以不依赖裁判的那部分规则在 shadow 下保留；裁判结论会引起的一切都不发生 |
| `active` | 问并生效 | 如上文 |

## 10. 选项（`mu.json` 的 `features.frame`）

| 键 | 默认 | 含义 |
| --- | --- | --- |
| `enabled` | `true` | 关掉后 `runtime.taskFrame()` 回到旧替身，其余功能照常 |
| `waitMs` | `3000` | 回合最多等任务帧多久，从消息到达算起 |
| `writerTimeoutMs` | `20000` | 写一版帧的时限 |
| `show` | `true` | 帧更新说明是否也显示在对话里 |
| `report` | `true` | 一轮结束、清单有变化时，是否告诉用户清单的进度（第 8 节） |

命令 `/frame`：版本、目标、每条约束及出处、子目标、验收条件及证据、未决问题、是否过期、上次失败原因。展示事件 `frame.updated`（载荷：原因 `created`/`updated`/`progress`/`stale`/`restored`、是否过期、完整的帧、未并入的原话），桌面端以后可以据此画任务帧条。载荷里只有用户自己的话和模型的一行证据，没有裁判原始输入。

## 12. 没有验证的（如实）

- **没有调用过真实的 Jev，也没有调用过真实的 writer 模型。** `task.frame` 的措辞没有在 judge-bench 上测过，0.6 / 0.7 两个阈值和“约束 + 纠正概率相加”都没有校准。writer 提示词对真实模型的 JSON 合规率、逐字拷贝率未知。
- 运行中途消息（steer / followUp）的路径有代码，**没有测试**。
- “完全没有模型 → 规则”在功能层没有会话级测试（测试环境里总有模型），只在纯模型层测了 `ruleUpdate`；“连续两次失败 → 规则”有会话级测试。
- 旧会话 resume 时用第一条用户消息生成第 1 版、`reload` 后重建：没有测试（树导航的重建测了，走的是同一个函数）。
- 说明消息在终端里用 pi 默认的自定义消息样式显示，没有写专门的渲染器，也没有在真实终端里看过。桌面端还没有消费 `frame.updated`。
- 没有在 Windows 上运行（本包没有路径或进程相关的代码）。

## 13. 已知的缺口

- **约束只是被记录并告诉模型，没有在工具调用层强制执行。** PRD 验收“用户说‘先别修改’后，所有新发起的写操作受到约束”**尚未满足**：`guard` 还不读约束。这是下一步最该做的。
- **子代理拿不到帧。** `delegate` / `hive` 的子代理提示里没有父会话的约束，PRD 验收“约束不因子代理调用而消失”**尚未满足**。`runtime.frame` 已经可读，接上只差 `swarm.ts` 里的几行。
- 运行中因上下文溢出而自动压缩并续跑时，说明要到下一条用户消息才重发。
- 用户把排队中的消息撤回后，它对帧的影响不会回滚（帧条目会在下一个回合落盘）。
- 拒绝执行的提示（没选模型、没登录）仍会生成第 1 版，和旧替身行为一致。
- 回合号在扩展重新加载后从头计数，跨重启不连续；条目 id 才是可靠出处。
