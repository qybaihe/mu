# 目标模式（`/goal`）

更新日期：2026-09-22。状态：已完成并测试（harness）。第二版：**是否达成改由大模型判断**，判定器退为兜底。桌面端还没有对应的界面，展示事件 `goal.state` 已经带上判断理由和下一步。

## 1. 要解决什么

长任务里最常见的失败不是做错，而是**停早了**：模型说一句“基本完成了”就收工，用户回来才发现测试没跑、验收条件还开着。pi 上游没有“目标模式”（查过：示例扩展里有 plan-mode、todo、handoff，没有自动续跑）。Claude Code 的 `/goal` 是用一个 Stop hook 把会话拦住。mu 的做法是：每次模型想停，都由一个**读证据的判断者**决定停不停，并且让**事实压过说法**。

## 2. 怎么用

| 命令 | 作用 |
| --- | --- |
| `/goal <条件>` | 定下目标并立刻开工。条件用你自己的话写，例如“packages/x 的测试全部通过，README 写明新开关” |
| `/goal` | 没有目标时：**弹出输入框问你条件**，填了就进入目标模式。有目标时：显示目标、状态、上次判断的理由和下一步 |
| `/goal clear` | 取消（`off` / `stop` / `none` 同义） |

目标在跑时，状态栏显示 `goal 3/20`（第几次续跑 / 额度），暂停时显示 `goal paused`，达成后显示 `goal met`。

条件本身会像你的普通消息一样进入任务帧：writer 据此写出验收条件，这些条件就是 to-do 清单，也是判断“做完没有”的事实依据。

## 3. 谁来判断：大模型，判定器兜底

第一版让判定器对结束语回答两个是非题（“是否已达成”“是否在向用户要东西”）。用户的反馈是：**Jev 判断结束不准**。它只读一句结束语，读不出“测试其实还红着”“这一轮在重复上一轮”。所以第二版换成：

- **默认（`checker: "model"`）**：由大模型判断，默认用当前会话的模型（`checkModel` 可以另指定，写成“提供商/模型”；`checkThinking` 设思考等级，默认不思考）。
- **兜底**：大模型没答上来（调用失败、超时、回复不是要求的 JSON）时，交给判定器的判定点 `goal.met`；判定器也不可用时，只看事实。
- 也可以设 `checker: "jev"`，回到第一版的做法。

**判定器在这里做什么**：维护任务帧（验收条件就是它和 writer 一起写出来、逐条勾掉的），以及兜底。这正是它擅长的：有任务帧做辅助时判断准，单独读一句话判断“做完没有”则不行。

### 大模型读到什么

每次模型想停，判断者收到一份证据（`src/goal/check.ts`）：

- 目标原文；这是第几次续跑、额度多少；上一次判断给出的“下一步”（用来看这一轮有没有照做，还是在原地打转）。
- **事实**：没勾掉的验收条件；改过但之后什么都没跑的文件；**最近一次检查命令**（测试、构建、类型检查、lint）是哪条、过没过、输出的最后一段。
- 这一轮做了什么：每个工具调用一行，比如 `bash npm test -> error`。
- 模型的结束语。

它回一个 JSON：

```json
{"verdict": "met | continue | needs_user", "reason": "一句话理由", "next": "下一步，具体到能直接动手", "stalled": false}
```

要求它严格：只有证据表明达成才算达成，模型自己说“做完了”不算证据。`reason` 和 `next` 用目标所用的语言写，中文目标就是中文理由。证据里的文字一律当数据，不当指令。

## 4. 每次模型想停下来时发生什么

1. 你按了 Esc → 暂停（“你打断了运行”）。模型调用失败 → 暂停。这两种都不去判断。
2. 判断（见上），然后按顺序处理：
   - **需要你** → 暂停，并把判断者说的原因告诉你（“要你选数据库”）。向用户提的问题，绝不能靠“继续干”来回答。
   - **有没勾的验收条件，或改完没跑过** → 继续，不管判断者和结束语怎么说。
   - **达成** → 达成，理由显示给你。
   - **继续** → 发一条 `kyrn.goal` 消息让它接着干：目标原文、**为什么还没达成**、**下一步**、未完成的验收条件、未验证的文件、第几次续跑。
3. **原地打转**：判断者说这一轮在重复自己（`stalled`），续跑消息会明确要它换个思路；连续 `stallLimit`（默认 2）次都是这样，就暂停下来问你怎么走。

### 自己会停下来的情况

| 情况 | 说明 |
| --- | --- |
| 模型需要你 | 见上，带原因 |
| 你打断 / 模型调用失败 | 不会顶着错误空转 |
| 连续空转 | 连续 `idleLimit`（默认 2）轮一个工具都没调用就结束 |
| 原地打转 | 连续 `stallLimit`（默认 2）次被判断为没有进展 |
| 续跑次数用完 | `maxContinuations`，默认 20，从你上一次发言算起 |
| 时间用完 | `maxMinutes`，默认 180，从你上一次发言算起 |

暂停之后，**你发的下一条消息就是“接着干”**：目标恢复，额度重新计。重新打开会话时，原来在跑的目标以“暂停”状态回来，不会自己启动（你可能已经不在电脑前）。

## 5. 设置（`features.goal.*`）

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `checker` | `"model"` | `"model"` 或 `"jev"` |
| `checkModel` | `""` | 判断用的模型；空 = 当前会话的模型 |
| `checkThinking` | `"off"` | off / minimal / low / medium / high |
| `checkTimeoutMs` | 90000 | 超时就退回判定器，再退回只看事实 |
| `stallLimit` | 2 | 连续几次没进展就暂停 |
| `maxContinuations` | 20 | |
| `maxMinutes` | 180 | |
| `idleLimit` | 2 | |

代价：每次续跑多一次模型调用，输入是几百到一两千个 token 的证据（不是整段历史），输出几十个 token。用当前会话的模型最省事；想省钱可以把 `checkModel` 指到便宜又靠谱的模型上。

## 6. 与其它功能的关系

- **完成核对**（`turn.completion`）：目标在跑时它让位，因为目标模式带着同样的事实发同一类提醒，两个声音没有意义。
- **任务帧 / to-do**：验收条件是事实来源。没开任务帧时只剩“改完没跑”“最近一次检查”两类事实和判断者的读法。
- **硬约束把关**：照常生效。续跑不会绕过你的约束。
- **会话树**：状态（含上次的理由、下一步、谁判断的）存成 `kyrn.goal` 条目，回退或分叉之后恢复的是那个分支上的目标。

## 7. 验证情况

`test/goal.test.ts`，14 个用例（faux 模型 + `MockJudgeProvider`，判断者的回复是脚本化的模型回复）：

- 大模型判断：继续 → 达成的完整序列，续跑消息带上理由和下一步，判断请求里确实有目标、这一轮的步骤、最近一次检查、结束语，且判定器一次都没被问；判断者说达成但改完没跑 → 照样继续；需要你 → 暂停并带原因；连续两次原地打转 → 第一次要它换思路、第二次暂停；判断者回复不是 JSON → 退回判定器；只输入 `/goal` → 弹框问条件、进入目标模式、状态栏跟着变；证据的格式与回复解析。
- 判定器兜底（第一版的 7 个用例照旧，改为显式选 `checker: "jev"`）：策略每一条分支、连续空转、提问时暂停、额度、影子模式只认事实、`/goal clear`、条目解析。
- 变异检查：去掉“事实压过判断者的达成”，对应用例失败；去掉原地打转计数，对应用例失败。

未验证：真实模型当判断者的准确率与成本（需要真实长任务来量）；打断（Esc）路径只有代码；桌面端界面。
