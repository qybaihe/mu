## 结论

**Jev 已有局部正向作用，但当前记录不足以证明整体价值很大或净收益为正。**

最明确的是技能说明隐藏和蜂群信息过滤。工具输出准入在本批样本中没有删掉任何块，却消耗最多的判断输入；浏览器的判定很快，但多数任务未闭环。应按决策点验收，不能把所有 active 判定视作收益。

- 排除没有真实 provider 响应的测试目录；不把本次回测 hive 纳入样本。真实 provider 运行仍可能是开发验证任务，不等于生产任务。

## 分项结果

### 1. 工具输出准入：本批样本没有兑现节省

完整主历史与子代理合并后：

- 194 批、2,412 个块。
- 2,385 个 result、6 个 error、21 个 unknown。
- `drop=true` 为 0；实际工具结果中也没有找到该功能的归档裁剪标记。
- 输入 1,966,585 tokens，占已记录 Jev 输入约 54.0%。
- 每批墙钟 p50 1,351ms，p95 3,807ms。各批耗时可重叠，不能相加后当作用户额外等待。

这不是“Jev 应该删掉源码”的证据。多数候选可能确实应保留；问题是当前触发器花了大量成本去确认无需裁剪的内容。应先改进候选初筛与收益评估，不是为了制造节省而放宽删除阈值。

### 2. 技能披露：有直接的上下文暴露收益

在可核对首轮落地的 13 个主会话/运行实例中，实际隐藏 511 个技能描述实例，中位数约 40 个，涉及 42 个不同技能。511 不是 511 种技能。

全量账本有 55 条披露判断，其中 hide 名称累计出现 2,178 次；后续查询可能只用于提示相关技能，不能把这些 hide 结果全部算成新隐藏。缺少候选 state，未给出精确字符或 token 节省。

隐藏动作可证实；选择是否正确、是否漏掉必要技能、是否提升完成质量，仍缺独立标签。跨 reload 状态持久化正在开发，见 07 文档。

### 3. 蜂群：信息量明显收敛，任务增益尚未证明

6 次真实 provider hive 的 gate 记录：

- publish：662 个候选、89 个通过，约 13.4%。账本对应 663 个 item，存在 1 项落地记录差异，不能假定每次判断均完成发布记录。
- deliver：140 对候选、64 对通过；其中 16 个通过来自 decision 类消息的确定性强制投递，不归因 Jev。
- 实际注入收件蜂的 delivery 为 63 条；64 个通过中有 1 个没有落地。
- 89 条白板信息中，40 条至少送达一只蜂。
- board 到实际收取的延迟中位 27.2 秒、p95 76.2 秒，说明判断快不等于信息立刻被消费。

抽样与词汇复用检查观察到部分信息进入后续报告，但未找到强证据证明某条投递立即改变调查并解决任务。词汇复用只能作线索，不能作“成功采纳率”；未复用也不能自动判为无价值。

30 只真实 provider 子代理中，24 个正常 settled、2 个确认取消、4 个旧记录没有完整收尾证据。这里的正常退出、看门狗、取消、部分报告回收属于确定性运行时代码的效果，不是 Jev 的任务成功率。

### 4. 浏览器：判定速度有优势，当前闭环可靠性不足

可识别真实公网 browse 18 次，其中直接 Jev 14 次：2 done、10 blocked、2 执行异常。开发/验证任务占比较高，不能外推到任意网站。

42 条 Jev browser.step 判定延迟 p50 288ms、p95 938ms。有结果的失败以连续无进展、无可行动作为主。两个 Jev done 有最终页面的可见佐证，但 done 本身仍由同一 judge 判定，缺独立成功验证器。

历史存在同类 MDN 目标 Jev 成功、其他判断后端失败的正向案例；模型、版本和页面状态不严格相同，不是随机对照。当前证据支持“可以低延迟作页面选择”，不支持“浏览器整体已经稳定高效”。

### 5. 主动遗忘：有小量收益，必须与规则分开

Jev 11 个候选中选择 3 个 shrink（2 个 bash、1 个 delegate）；可重建的单次投影约少发 27,654 字符，不是 tokens，也不是跨所有后续请求的累计节省。

另有约 156,744 字符的旧读取替换来自“后续读取取代旧读取”的确定性规则，不能算作 Jev 收益。对这些裁剪的长期重读代价、缓存代价与正确性仍没有完整测量。

### 6. 归类、漂移、经验：有动作，但收益未闭环

- Preflight：全量 25 条判定；有明确展示落地证据的 13 次中，4 次改 thinking（2 次降档、2 次升档），9 次提供 hint。其余不能仅凭账本推定实际应用；有 timeout/abstain。
- Drift：252 次判断，195 on_track、51 unknown、3 loop、3 drift。仅 6 个纠偏候选，没有验证它们实际救回了多少任务。
- Memory capture：6 次全部 skip，没有查到对应经验捕获/召回收益。这不证明应该捕获更多，只说明当前样本没有可验收效果。
- Locate、子代理角色/模型选择确有使用，缺少定位正确率与对照路由的任务结果，暂不量化收益。

## 如何判断价值是否“大”

现在能确认的是机制效果，不能确认经济或任务上的因果净收益：

1. 账本有效答案不等于正确答案，active 不等于实际应用。
2. 少传文本不等于少付钱；还要算判断/Writer/重试、缓存损失、补读和任务耗时。
3. 筛选率不等于筛选准确率；被挡掉的信息可能包含关键证据。
4. 目前没有同任务的无 Jev 对照，也没有统一的成功、返工和人工干预标签。
5. 判断 token 与主模型 token 单价不同，不能直接相减计算 ROI；缺失的 batch 输出用量也不能视为零成本。

## 建议（本次未修改开关或实现）

- 优先保留并校准技能披露、hive 发布/投递；抽样复核拒绝项，验证是否漏掉重要能力或证据。
- 工具输出准入优先做规则初筛、候选类型识别与收益统计，避免仅因输出长就全部交给判定器；不要用激进删除提高表面收益。
- 浏览器先补独立目标验证、无进展恢复和固定网页任务集，再谈扩大使用。
- 归类、漂移、经验逐项建立“判定 → 实际动作 → 后续结果”关联，记录超时和未采用原因。
- 后续在用户批准的固定任务集上比较规则-only、Jev shadow、Jev active；分别衡量成功率、关键约束保留、总输入/缓存、墙钟、费用、返工和人工干预。先固定版本与测试条件，避免把不同任务的历史耗时当 A/B。

本次交付是观察性回测，不是线上因果实验；没有依据宣称 Jev 已带来某个百分比的成本或成功率提升。
