# KYRN Harness PRD：以 pi 为底座，深度融合 Jev

> 已于 2026-09-21 更名为 mu（命令 `mu`，标识 μ）。本文是更名前的记录，正文保持原样；新旧名对照见 [10-rename-to-mu.md](10-rename-to-mu.md)。

> 版本：v0.1 · 状态：待评审
> 定位：面向复杂开发任务的判断驱动型 Agent Harness
> 范围：产品目标、核心体验、功能边界、验收标准与演进路线；不是实现设计稿。
> 依据：当前仓库的 Jev 构思、注入点和桌面集成文档。现状描述不代表本次已重新完成代码审计或线上验证；性能指标均为待验证目标。

## 1. 产品定义

**KYRN 是建立在 pi 之上的 Agent Harness：让主模型负责理解、规划和生成，让 Jev 持续判断什么值得看、下一步如何执行、结果是否足以交付，由确定性代码执行策略并守住权限边界。**

Harness 指模型之外的运行系统：管理上下文、工具、会话、子代理、执行权限与验证证据。

本文 Jev 指 TypeSafe 的判断模型。它基于给定状态回答是非题、闭集选择题和评分题，不承担开放式规划、代码生成或摘要写作。

### 核心产品主张

不是给 pi 增加一个偶尔调用的 `judge` 工具，而是让 Jev 参与任务生命周期中的关键决策：

1. **执行前**：判断任务类型、复杂度、需要哪些能力，以及是否值得并行。
2. **执行中**：筛选工具输出、分配子任务、控制跨代理信息传播、发现偏航。
3. **交付前**：把模型的完成声明与真实验证证据对应起来。
4. **交付后**：记录决策和结果，让判断策略可以评测、校准和撤回。

**深度融合的标准不是调用 Jev 的次数，而是：在不降低任务质量与安全性的前提下，减少无效上下文、无效主模型回合和人工盯守。**

## 2. 用户问题与机会

### 2.1 当前问题

| 用户遇到的问题 | 具体表现 | KYRN 的解决方向 |
| --- | --- | --- |
| 上下文越长，代理越容易偏离目标 | 数千行日志和过时文件内容挤占有效信息 | 在输出进入上下文前筛选，保留可召回原文 |
| 简单任务过度思考，复杂任务投入不足 | 改一个文案启动多个代理，排查并发问题却一直低档重试 | 根据任务特征选择执行档位，保留用户指定设置 |
| 多代理并行但没有形成协作 | 多个调查者重复查同一原因，或互相灌入整段历史 | Jev 判断哪些发现值得分享、应该发给谁 |
| “已完成”不等于真的完成 | 改完代码没验证；测试通过后又改文件仍声称通过 | 建立与当前代码版本绑定的完成证据 |
| 自动化过程不透明 | 用户不知道为何切模型、隐藏输出、停止子代理 | 展示实际决策、实际动作、证据和降级原因 |
| 经验积累变成上下文负担 | 所有历史偏好、技能和教训每轮都加载 | 按需检索和披露，而不是全量注入 |

### 2.2 一个典型例子

用户要求：“修复登录态偶发丢失，不改公开 API，并补回归测试。”

普通执行中，代理可能读取大量日志、重复搜索、遗漏“不改 API”的约束，最后仅凭一次命令成功退出就宣称修复。

KYRN 应保持一份明确的任务状态：目标是修复登录态，硬约束是不改 API，验收需要复现证据和回归测试。长日志只把相关片段送给主模型；无法确定根因时，由多个调查者分别验证缓存、并发和认证链路；交付时检查当前版本的回归结果，而不是判断回复“听起来像完成”。

这些机制是完成复杂任务所必需的。自动切换大量模型、自动生成长期记忆和复杂蜂群拓扑是后续优化，不作为首版成立的前提。

## 3. 目标用户与产品范围

### 3.1 首要用户

- **日常使用编码代理的开发者**：希望更少返工、更少重复授权和更低的成功任务成本。
- **处理疑难问题的工程负责人**：需要并行调查，但要求发现有来源、分歧可见、修改可控。
- **开发 Agent 应用的工程师**：需要可嵌入、可观测、可替换判断模型的运行层。

首个场景聚焦真实代码仓库中的缺陷修复、功能修改和技术调查。网页检索作为辅助能力，不以通用浏览器自动化或办公自动化平台为首发定位。

### 3.2 用户希望完成的工作

- “交给你一个目标，你判断需要投入多少能力，不要让我一直手动选工具和模型。”
- “长任务中记住我的约束，别让我重复解释。”
- “需要多人调查时可以并行，但不要重复劳动或互相覆盖文件。”
- “告诉我做了什么、验证了什么、还有什么没做，不要只说完成。”

### 3.3 不做什么

- 不替换 pi 的模型接入、基础工具、会话系统和 Agent 循环。
- 不把 Jev 当作主模型、通用规划器或唯一安全判断者。
- 不默认替用户提交、推送、发布、支付、删除或发送外部消息。
- 不在首版实现多代理同时修改同一工作区。
- 不以“永不丢信息”“零幻觉”“全自动完成任意任务”为承诺。
- 不另建桌面壳和第二套配置系统；沿用现有桌面端的接入方向。
- 不把共享配置、历史回放描述为 CLI 与桌面的实时共同控制。

## 4. 产品目标与原则

### 4.1 目标

**主目标：在任务质量不下降的前提下，降低每个被验证解决的任务的总成本和人工介入次数。**

同时关注三个结果：

- **更聚焦**：主模型主要看到与当前任务相关的信息。
- **更可靠**：完成结论有证据，遇到不确定性会明确降级或停下。
- **更可控**：用户知道系统做了哪些判断，并能覆盖、暂停和关闭。

### 4.2 决策原则

1. **规则先行，Jev 处理语义灰区。** 明确权限、参数校验、预算和重复调用检测不交给概率判断。
2. **Jev 判断，代码执行，主模型生成。** 题面、答案和动作是三层，不让 Jev 直接执行命令。
3. **不确定就弃权。** 高分不等于正确率；阈值按决策类型校准，不使用一套阈值控制所有功能。
4. **先减少入口噪音，再处理历史膨胀。** 避免为了省 token 破坏提示缓存，反而提高成本。
5. **可优化的行为必须可退回，安全约束不能退回。** Jev 不可用时关闭优化，不自动取消权限闸门。
6. **事实比完成声明重要。** 验证失败、未执行、过期和环境受阻必须区分。
7. **用户明确选择优先于自动路由。** 固定模型、只读模式、先计划、暂不执行等要求不能被 Jev 覆盖。

## 5. 核心体验：三个闭环

### 5.1 上下文闭环

```text
任务目标与约束
  → 工具调用及其意图
  → 原始结果归档
  → 规则保护关键内容
  → Jev 判断候选片段相关性
  → 精简结果进入主模型
  → 必要时召回原文
  → 记录误筛反馈
```

用户看到的是“隐藏了哪些内容、为什么、如何展开”，而不是被静默删除的信息。

### 5.2 执行与协作闭环

```text
任务分类
  → 单代理 / 独立任务并行 / 同一难题多角度调查
  → 分配角色、模型档位、思考强度和预算
  → pi 执行
  → Jev 筛选跨代理发现
  → 主模型综合证据并决定下一步
```

`delegate` 用于互不依赖的子任务；`hive` 用于同一个未知问题的协同调查。首版由主模型或用户显式发起，不让一个低置信判断自行展开昂贵蜂群。

### 5.3 完成与反馈闭环

```text
任务验收条件
  → 代码变更与验证运行
  → 证据绑定当前产物版本
  → 确定性检查证据有效性
  → Jev 判断声明与证据是否相符
  → 已验证完成 / 已实现但未验证 / 部分完成 / 受阻
  → 用户反馈与决策复盘
```

三个闭环共享任务状态、权限、预算和决策账本。它们不是三个互不关联的插件。

## 6. pi、KYRN 与 Jev 的职责边界

```text
CLI / TUI                         桌面端
    │                               │ ACP 适配 → RPC
    └────────── KYRN 运行层 ─────────┘
                   │
      任务状态 · 策略 · 预算 · 权限 · 证据 · 账本
                   │
          统一判断接口 → Jev
                   │       仅返回类型化答案
          pi 扩展 / SDK / 事件
                   │
       pi 会话 · 模型调用 · 工具执行 · 事件流
                   │
             模型 / 工作区 / 外部系统
```

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| pi 底座 | 模型与认证接入、Agent 循环、工具、会话、压缩与分支原语、SDK/RPC | KYRN 的业务判断策略 |
| KYRN 运行层 | 任务状态、判断编排、上下文策略、子代理协作、审批、证据和可观测性 | 重写一套 pi |
| Jev | 在限定状态和候选中分类、选择、评分 | 生成代码、制定开放式计划、授予权限 |
| 主模型 | 理解需求、规划、生成、综合分歧、处理升级问题 | 承担所有高频机械分拣 |
| 客户端 | 展示过程、接收输入、审批与控制 | 再实现一套调度或判断逻辑 |

### 实现约束

- 首先复用 `packages/kyrn-judge` 及 pi 现有扩展接口，不因产品分层立即拆出多个包。
- 仅当必要能力无法通过现有接口实现时，增加小范围、独立可测试的 pi 补丁。
- 会话事实沿用 pi；新增判断、证据和展示记录通过稳定关联 ID 连接，不维护相互矛盾的聊天历史。
- 当前主 CLI 不应直接假定运行在 `packages/agent/docs/harness.md` 描述的实验性持久化 Harness 上。该规范中的恢复、远程会话和其他未完成能力不是本 PRD 的现成底座。

## 7. 功能需求

优先级定义：**P0 = 首版必须闭合；P1 = 首版成立后的增强；P2 = 实验方向。** 已有功能不因被列为 P1/P2 而删除，只是不作为首版推广或自动启用的承诺。

### FR-01 统一判断内核与决策账本 · P0

**需求**

- 所有 Jev 调用经过同一入口，统一执行状态裁剪、脱敏、超时、预算、能力检查与记账。
- 每个决策声明：唯一 ID、题面版本、输入范围、候选动作、弃权条件、失败策略和缓存影响。
- 支持 `off`、`shadow`、`active`：关闭；只观察不改变行为；按策略生效。
- Jev 为首选判断后端；直连或网关由用户配置。保留替代后端接口，但不默认把它们视为能力等价。
- 批处理兼容的问题；超过后端限制时分批或弃权，不能无提示截断关键约束。
- 超时、无权限、答案缺失、越界概率、未知选项、预算耗尽和低置信均产生明确结果。
- 只有与当前任务版本匹配、尚未过期的判定可以生效。晚到结果不能覆盖新用户指令。

**验收**

- 每个已应用动作均可关联到规则或判断记录；纯规则动作标明来源。
- 相同状态重复判定可去重；缓存键至少区分任务版本、题面版本、策略版本和判断后端版本。
- `shadow` 不改变工具结果、模型档位或上下文。观察本身仍会产生判断成本，界面与统计必须说明。
- Jev 断网时，优化按降级策略退出；不存在无限等待或自动扩权。

### FR-02 任务状态与约束保留 · P0

**问题**：只把首条消息当目标、最新消息当子目标，无法正确处理“保留原方案，但取消数据库变更”。

**需求**

- 维护 Task Frame：目标、用户硬约束、当前子目标、验收条件、未决问题、预算和版本号。
- 生成由主模型或已配置的 writer 模型完成；Jev 只判断是否需要更新、是否冲突、候选是否相关。
- 硬约束保留用户原文及来源，不为满足约 200 token 的摘要预算而丢弃。展示摘要可以短，权威记录不能有损覆盖。
- 任务切换、用户纠正和子目标变化时更新版本；旧判断、旧完成结论按适用范围失效。
- 更新失败时保留上一有效版本并附加新用户原文；暂停依赖准确任务状态的激进筛选。
- 新增工具调用意图优先复用现有任务说明；统一 `intent` 参数属于后续可选增强，不阻塞 P0。

**验收**

- 用户要求“先别修改”后，所有新发起的写操作受到约束，而非只出现一条提醒。
- 约束不因压缩、子代理调用或会话恢复而消失。
- 无法确定是追加任务还是替换目标时保留歧义并澄清，不静默覆盖。

### FR-03 输入预检与执行档位 · P0

**需求**

- 识别问答、单点修改、多步实现、调查、方案讨论和无法分类。
- 输出少量可解释的档位：轻量、标准、深入调查；映射到思考强度、能力披露和并行建议。
- 自动路由不能覆盖用户锁定的模型、思考强度、只读范围和“先给方案”的要求。
- 用户发出停止、取消、禁止修改等明确控制指令时，优先由控制路径处理，不等待 Jev 分类。
- 等待预检期间立即显示已收到消息、正在判断和可跳过操作。

**验收**

- 简单问答不自动开启蜂群或完成验证循环。
- 预检超时可按当前配置开始执行，晚到结论只记账、不改变正在运行的本轮。
- 非安全类预检等待上限初始建议为 2 秒，可配置；跳过后不能留下永久加载状态。

### FR-04 工具输出准入与可逆上下文管理 · P0；历史遗忘 · P1

**需求**

- 首版优先处理长日志、搜索结果和重复进度信息，不默认裁剪源码、diff、用户指令或验证证据。
- 先保存完整可用原文，再分块筛选；保存失败时保留内容，不创建虚假召回入口。
- 错误、失败用例、关键警告和无法分类的块默认保留。不能仅因属于 `warning` 或 `passing` 就判定无关。
- Jev 必须结合任务目标与调用意图判断相关性，而不只做输出类型分类。
- 被隐藏内容留下来源、范围、稳定句柄和召回入口；召回不得依赖重新运行原工具。
- 归档内容至少与会话保留期一致，限制访问权限；不能只依赖可能被系统清理的临时目录。
- 工具调用与结果保持协议配对，保留调用 ID、错误标记和关键结构化字段。
- P1 再做历史遗忘：优先处理过期读取和重复结果，按缓存边界批量应用，并与压缩共享评分。

**验收**

- 在长日志中插入首部、中部、尾部失败证据，均不可因位置或长度而丢失。
- 隐藏内容可在当前会话及重启恢复后完整召回；显示过期版本来源，不能冒充当前文件状态。
- 不能将“相同命令又执行过”视为旧结果必然无用，例如修复前后的失败/成功输出都可能是必要证据。
- 自动裁剪无法安全满足上下文预算时，降级到 pi 的正常压缩，不无限重复判断。

### FR-05 有证据的完成判定 · P0

**问题**：“改完文件后执行过任意命令”不能证明任务通过；例如 `git status` 成功不等于测试通过。

**需求**

- 从任务验收条件形成验证清单，并遵守项目约定和用户禁止事项。
- 每次验证记录：检查类型、命令或检查动作、目标范围、退出码、结果摘要、原始证据和工作区版本标识。
- 在验证开始前捕获相关产物指纹，完成后检查期间是否变化；不能把对旧内容执行的检查绑定为新内容已通过。
- 再次修改相关文件、配置或依赖后，对应证据标为过期；不能只依据最后一次成功命令。
- 先由代码判断证据存在性、成功状态及版本有效性，再由 Jev 辅助判断完成声明与证据是否相符。
- 证据不足时最多自动发起一次补验回合；仍不满足则如实结束为未验证、部分完成或受阻，不形成无限循环。
- 验证未被授权或环境不可用时，不绕过限制；说明原因和用户可采取的下一步。

**交付状态**

| 状态 | 含义 |
| --- | --- |
| 已验证完成 | 已满足明确范围内的验收条件，且证据对应当前产物 |
| 已实现，未验证 | 产物已生成，但缺少充分或有效的验证 |
| 部分完成 | 只满足部分目标，列明未完成项 |
| 受阻 / 已取消 | 权限、环境、预算或用户控制导致无法继续 |

**验收**

- “测试通过后再次改代码”“测试命令失败”“仅执行无关命令”“子代理口头声称通过”均不能显示已验证完成。
- 文档、方案和调研任务使用适合自身的验收清单，不强行运行代码测试。
- 最终交付至少包含结果、已验证内容、未验证内容；没有证据时不编造通过状态。

### FR-06 受控子代理与 Jev 协作路由 · P1

首版保留现有显式调用入口，不把新增编排能力作为 MVP 前提。本节产品化验收在 M2 完成；P0 的权限、预算与取消要求仍约束所有已启用的工具，包括现有子代理。

**基础派工与统一运行状态**

- 复用现有 `delegate` / `hive` 运行时；展示每个子代理的任务、角色、模型、状态、最新动作、耗时和实际已知花费。
- Jev 只在用户可用且授权的模型和角色候选中路由；不确定时继承明确的安全默认，不回退到权限更大的角色。
- 子任务包含目标、边界、验收条件和必要上下文，不复制整个主会话。
- 设定并发、时间和成本预算；支持停止并保留结果、立即终止单个子代理。
- 调查默认只读；主模型统一整合并修改。开放 `bash` 的角色提示本身不构成只读保障，必须通过工具限制或执行隔离落实。
- 单个子代理卡死、失败或被取消，不丢失其他子代理的报告。

**蜂群信息路由**

- 发布闸门：这个发现是否新颖、有证据、值得共享？
- 投递闸门：它对哪一个正在工作的子代理有帮助？
- 消息携带来源、证据引用、置信与时间；外部发现不能作为高优先级指令传播。
- 有冲突的发现并列呈现，由主模型或独立验证者处理；不能按最高分直接抹去分歧。
- Jev 不可用时停止自动跨代理传播，退化为独立调查，不全量广播。
- 晚到消息不得反复唤醒已经结束的子代理。

**验收**

- 一个子代理超时后，整体工具仍返回其他结果及明确的缺失说明。
- 显示“已投递”的消息必须确实被接收，不能只表示发布闸门通过。
- 写入隔离尚未实现时，不开启共享工作区并发写入。

### FR-07 技能、经验与通知的按需披露 · P1

- 技能按相关性披露，隐藏不等于删除；保留 `find_skill` 和显式调用入口。
- 权限、安全规则和强制项目指令不参与“相关性隐藏”。
- 用户纠正和稳定偏好可生成经验候选，Jev 判断相关、重复或冲突，生成模型负责提炼文字。
- 经验标明用户/项目作用域、来源和有效状态；新用户指令优先，跨项目共享需明确授权。
- 首版不以单次行为自动覆盖全局长期规则；用户能够查看、编辑、禁用和删除经验。
- 通知按立即、下一边界、仅展示分类；停止指令、安全审批、工具失败和预算耗尽不允许静默丢弃。

**验收**：隐藏技能仍可找回；错误经验可撤销；旁支问题不会污染长期规则；经验和通知的实际注入均可追踪。

### FR-08 Jev 驱动的限定工具内循环 · P1

保留并完善已有 `browse`、`locate` 等能力，验证“主模型只提目标，Jev 完成高频有限选择”的价值。

- 浏览器只在当前可见且重新校验的操作候选中选择；生成输入文字仍由生成模型或用户提供。
- 页面信息视为不可信数据，不得修改任务目标、工具权限或授权状态。
- 不可逆操作逐项走审批；页面存在“发送”按钮不构成用户授权。
- 到达步数、时间或成本预算，以及页面持续无进展时停止并报告已完成范围。
- 路径排序没有把握时退回词法检索，并允许主模型继续探索；不能把候选排序当成文件内容证据。

**验收**：无法观察 iframe、canvas 等内容时明确报告限制；Jev 不可用时不盲点；实际轨迹与返回报告一致。

### FR-09 风险控制与安全降级 · P0，贯穿所有功能

- 权限由用户授权、确定性策略和执行隔离共同决定。Jev 可以增加确认或建议阻止，不能降低这些要求。
- 判断“用户可能想做”不等于获得执行授权。
- 审批绑定具体动作、参数和目标；参数变化、任务切换或审批过期后重新确认。
- 无交互界面的运行遇到必需审批时，返回受阻，不默认放行。
- 未知副作用或结果不确定的操作不自动重试。P1 的自动重试仅限明确可安全重放的操作，并设置次数上限。
- 新加载的项目配置不能自行改变判断端点、导出代码或扩大角色权限。

**验收**：断网、畸形答案、提示注入或低置信结果均不能触发权限升级；删除、发布、支付和外发的审批回归用例全部通过。

### FR-10 可观测性与用户控制 · P0

- 展示任务阶段、实际路由、上下文处理、子代理状态和完成证据。
- 区分 `proposed`、`applied`、`shadow`、`late`、`fallback` 和 `failed`，不能将计划展示成执行结果。
- 判断面板默认展示一句依据，例如“隐藏重复进度，保留全部失败信息”；详细概率和题面放在展开层。
- 概率显示为模型评分，不标成“正确率”；原因来自规则/策略或证据，不伪造 Jev 推理文本。
- 用户可按决策点关闭自动化、固定模型、召回隐藏输出和停止任务。
- 展示失败不能影响执行；观测事件不进入主模型上下文。

## 8. 核心数据对象

以下是产品需要保存的语义字段，不限定最终存储格式。

| 对象 | 必需信息 | 作用 |
| --- | --- | --- |
| Task Frame | taskId、版本、目标、硬约束原文与来源、子目标、验收条件、预算 | 所有判断共用的任务依据 |
| Decision Record | decisionId、决策类型、题面/策略/模型版本、任务版本、状态摘要或哈希、答案、动作、耗时、用量、降级原因 | 区分判断与实际应用，支持评测 |
| Artifact Reference | artifactId、会话/调用关联、来源、内容指纹、存储位置、保留策略 | 支持原文召回和版本辨认 |
| Verification Evidence | requirementId、检查动作、开始/结束产物指纹、结果、证据引用、有效/过期状态 | 支撑完成结论 |
| Agent Task | 子任务目标、工具权限、角色、模型、预算、状态、最终报告、引用 | 支撑可控派工 |
| Outcome Feedback | 决策关联、召回/纠正/升级等信号、来源、人工确认状态 | 支撑后续校准，不能直接当作真值 |

默认记录哈希、类型化答案和动作，不保存完整判断请求。**哈希不能重建输入**：只有用户明确启用脱敏样本留存，或提供独立评测数据，才支持完整离线重判。过程事件回放和重新调用模型评测是两种不同能力。

“被召回”“被用户纠正”只是可能的错误信号；例如召回也可能由任务变化导致，不能自动把它标为误删。

## 9. 交互与默认策略

### 9.1 默认使用方式

用户正常输入任务即可，不要求学习 Jev 的题型或概率阈值。

默认界面只回答四件事：

1. 当前在做什么？
2. 系统替我做了什么选择？
3. 有什么需要我确认？
4. 结果验证到了哪里？

### 9.2 终端与桌面

- TUI 提供简短状态行、可展开判断记录和子代理进度。
- 桌面端复用现有的会话、项目、模型菜单、代码预览和审批界面；协作面板展示同一运行层的事件。
- 模型、判断后端、预算和开关由 KYRN 配置作为唯一事实来源；客户端不复制密钥，也不自行切模型。
- 设置是否立即生效、下轮生效或需要重连，必须明确显示。
- 当前不承诺桌面接管一个已在 CLI 运行的进程；实时共享控制需要独立设计。

### 9.3 自动化默认值

- 所有新增语义决策先 `shadow`，通过对应评测后逐项启用。
- 用户可选择保守预设；安全闸门不受优化开关关闭影响。
- 主模型默认保持稳定，优先在新子任务中路由模型，避免频繁破坏缓存。
- 蜂群先显式发起；自动发起在 P1 通过预算和收益评测后再开放。
- 判断总费用单独展示，不用“Jev 很便宜”替代预算控制。

### 9.4 降级矩阵

| 场景 | Jev 不可用或弃权时 |
| --- | --- |
| 输出筛选、历史遗忘 | 保留原文，使用 pi 的正常上下文处理 |
| 任务档位、模型路由 | 保持用户配置和当前安全权限 |
| 技能披露 | 保留候选描述及发现入口，不激进隐藏 |
| 风险授权 | 执行既有权限规则；需要审批则继续等待或受阻 |
| 完成判定 | 使用确定性证据；证据不足标未验证，不能默认完成 |
| 蜂群消息路由 | 不传播新消息，各子代理独立继续 |
| 浏览器动作选择 | 停止工具内自动动作，返回部分结果或受阻 |
| 经验写入 | 不自动形成长期规则，保留待审候选 |

因此不能用一个全局“失败就放行”概括系统行为。

## 10. 验证方案与成功指标

### 10.1 对照实验

至少比较三组：

- **A：原生 pi 基线**。
- **B：pi + KYRN 确定性规则**，关闭语义判断，用来识别规则本身的收益。
- **C：相同环境 + Jev 决策**，用于验证 Jev 的额外价值。

统一任务集、代码快照、主模型版本、权限、外部工具、可用模型范围和预算。多次运行并报告波动；先逐项开启功能，再评测组合，不把收益全部归因于 Jev。

对于 `hive`，另做“同样数量、角色和模型的独立并行”与“启用 Jev 消息路由”的配对对照。

### 10.2 指标定义

| 指标 | 定义 |
| --- | --- |
| 任务成功率 | 达到预先约定验收条件的任务数 / 全部尝试任务数 |
| 每成功任务成本 | 全部尝试的主模型、Jev、writer、子代理及可计量工具成本 / 成功任务数，包含失败和重试成本 |
| 人工介入次数 | 每任务的纠偏、重复解释和救援操作；必需安全审批单独统计 |
| 完成误报率 | 被标为已验证完成但独立验收未通过的任务比例 |
| 关键内容误筛率 | 标注为必要证据却被隐藏且未及时恢复的内容比例 |
| 主上下文输入量 | 主模型每次请求输入量之和；缓存读写分别报告，不冒充唯一内容量 |
| 总任务耗时 | 用户提交到最终交付的墙钟时间，报告中位数及 P95 |
| 判断额外阻塞 | 判断层增加的关键路径等待，按决策点记录 |
| 重复调查率 | 被标注为重复且未新增证据的调查动作数 / 全部调查动作数；独立复核不计重复 |
| 有效投递率 | 经盲审判定能帮助接收者当前任务的消息数 / 全部实际投递消息数 |
| 证据采纳率 | 被最终有效结论引用的共享证据数 / 全部共享证据数；按证据 ID 去重 |
| 子代理异常率 | 超时、失去响应或超预算的子任务数 / 全部启动子任务数；用户主动取消单列 |

价格缺失、工具成本不可计量时报告已知成本和未知项，不显示虚假的完整总额。协作指标按预先编写的标注规则复核，有分歧时由第三方裁定，不能用 Jev 自身评分充当效果标签。

### 10.3 首轮试点目标

以下是产品假设，不是当前实测结果或对外承诺：

- 首先建立至少 100 个覆盖真实开发场景的试点任务，用于发现失败模式和估计方差，不直接作为正式收益结论。
- 正式评测前固定任务分层、每题运行次数、样本量和停止规则，采用配对对照及 95% 置信区间；依据试点方差与预设差异计算样本需求，不因中途结果有利而提前停止。资源不足时只发布试点观察。
- 在预先定义的长日志任务子集上，主上下文累计输入量中位数下降至少 20%。
- 在质量不劣于基线的前提下，每成功任务已知总成本下降至少 15%；否则不能宣称省成本。
- 任务成功率采用预设 2 个百分点的非劣效界限；报告置信区间，样本不足时只做方向性结论。
- 必须覆盖的安全回归用例中，未授权高风险执行为 0；完成证据过期用例误标通过为 0。这不是对真实世界零风险的承诺。
- 上下文召回、停止保留结果和超时降级的确定性测试全部通过。

不把社区延迟、价格或单次示例当作产品性能保证。所有在线调用目标应按部署地区、后端和网络条件重新测量。

### 10.4 必测场景

简单问答；单文件修改；长日志修复；跨文件功能；原因未知的缺陷；中途纠正；失败后重复尝试；Jev 断网；恶意工具输出；验证后再修改；归档后重启召回；子代理卡死；非交互审批；预算耗尽。

## 11. 非功能要求

### 11.1 可靠性与预算

- 判断调用、工具内循环和子代理运行均有明确超时、取消和预算出口。
- 判断预算预留必要安全控制空间；超预算先停止可选优化，不先关闭保护。
- 停止会阻止新动作并尽力取消运行中动作，但不承诺撤销已经发生的外部副作用。
- 进程恢复不能自动重放结果不确定的外部写操作；显示待核对状态。
- 不承诺通过 pi 会话恢复实现外部操作“恰好执行一次”。

### 11.2 安全与隐私

- 启用云端判断前，说明可能发送的用户消息、代码片段、工具输出及目标服务。
- 默认最小化输入并脱敏；密钥、凭据和完整原始状态不进入普通账本或展示事件。
- 脱敏不能保证消除所有敏感信息；敏感项目可禁用云端判断，不把“本地 Harness”等同于数据不出本机。
- 判断服务切换、训练样本上传和跨项目经验共享需用户明确授权。
- 本地归档、经验和账本支持保留期限与删除，说明 pi 会话、备份及远端服务的独立留存边界。
- 不把供应商旧目录中的数据政策描述当作当前合同保证。

### 11.3 可维护性

- 题面、策略、展示事件和证据结构版本化，支持固定版本回归。
- pi 补丁保留变更清单，每次升级验证扩展事件、工具配对、取消和完成边界。
- 展示使用实际事件与用量；缺失数据标未知，不估造成已知值。

## 12. 当前基础与产品化缺口

以下依据仓库文档，不等同于本次完成了实现验证。

| 领域 | 已有基础 | 本 PRD 要补齐的产品条件 |
| --- | --- | --- |
| 判断内核 | 多后端、决策规格、模式切换、账本 | 分决策校准、版本一致性、预算与降级验收 |
| 输入预检 | 分类、档位、等待面板、晚到状态 | 用户硬约束优先、明确的等待体验目标 |
| 任务状态 | 首条/最新消息的简化实现 | 带来源、版本与验收条件的 Task Frame |
| 上下文 | 工具准入、遗忘、抽取式压缩 beta | 会话级可靠归档召回、证据保护、缓存收益验证 |
| 完成检查 | 根据变更和命令行为进行补验提醒 | 验收条件与当前产物版本绑定，不把任意命令当验证 |
| 子代理与蜂群 | 路由、进度、白板、停止、看门狗 | 权限不升级、证据化报告、质量与成本对照 |
| 浏览器与定位 | Jev 驱动有限动作和文件候选排序 | 明确局限、审批回归和工具级收益验证 |
| 技能与经验 | 披露、召回与捕获能力 | 可编辑、作用域、冲突处理和留存策略 |
| 桌面 | 桌面端接入、协作面板、事件回放 | 运行状态一致性与完整的错误/降级体验 |
| 持久执行 | pi 会话保存及部分运行状态 | 不宣称已有完整跨进程执行恢复或 CLI/App 同时控制 |

相比继续增加决策点，当前优先级应是：**任务状态准确、原文可靠召回、完成证据可信、效果可量化。**

## 13. 交付阶段与准入条件

不先承诺日历排期；完成现状核验后再按人力估算。

| 阶段 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- |
| M0：建立基线 | 任务集、现状能力清单、成本/质量统计、统一降级矩阵 | 能稳定复现基线，并区分计划、判断与实际执行 |
| M1：可靠单代理闭环 | FR-01～05、FR-09～10 的 P0 要求；复用现有界面和预检，不新增协作编排 | 关键约束不丢、证据不误报、故障可降级；形成可发布的首版 MVP |
| M2：受控协作 | 明确权限的路由、报告证据、蜂群传播与停止体验 | 相对独立并行有可测收益，单个代理失败不拖垮任务 |
| M3：按需上下文 | 技能与经验管理、通知路由、缓存感知遗忘、自动化预设 | 质量达标，成本收益成立，无隐式扩权 |
| M4：策略优化 | 样本留存授权、回放校准、分项目策略和可选本地蒸馏 | 有足量可信标注，能安全回滚，用户数据用途明确 |

现有 `browse`、`delegate`、`hive` 保留作为可选能力；首版成功不依赖所有能力自动开启。

**首版发布闸门**：P0 用例全部通过；无已知未授权高风险执行问题；完成证据与召回链路可用；收益声明有对照实验支撑。达不到成本目标时可以作为实验版发布，但不能宣传已证明降本。

## 14. 主要风险与应对

| 风险 | 应对 |
| --- | --- |
| 判断高置信但错误 | 按场景校准、设置弃权、优先可逆动作、保留原始证据 |
| 高频判断增加等待和费用 | 批处理、去重、异步观察、预算、只保留有收益的决策点 |
| 筛选导致漏证据 | 保护关键内容、可靠召回、误筛评测、遇到不确定保留 |
| 缩短上下文却破坏缓存 | 入口优先、历史决策有粘性、按实际账单评测 |
| 多代理制造更多噪音 | 限制并发与传播预算、共享证据不共享整段历史、独立对照 |
| 模型自评形成虚假可靠感 | 代码验证和产物指纹作为事实依据，Jev 仅辅助比对 |
| 新功能与上游 pi 耦合失控 | 扩展优先、小补丁、边界测试，不提前迁移实验运行时 |
| 为了好看而展示不真实状态 | 只展示实际事件，明确未知、计划、已应用和失败 |

## 15. 待确认的产品决策

本文先按以下假设推进，评审时确认即可：

1. **首发用户**：以开发者为主，先把复杂编码任务做深，而不是通用办公 Agent。
2. **产品入口**：CLI/TUI 与现有桌面端接入共用一个 KYRN 后端，不另起桌面产品壳。
3. **自动化程度**：首版采用保守默认；蜂群与高成本路由显式发起，评测达标后再扩大自动化。
4. **主要承诺**：先证明质量不下降，再证明成功任务成本与人工盯守下降；不以 token 压缩比例作为唯一卖点。
